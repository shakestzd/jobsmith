Plan: Marimo review UI for jobsmith resumes — section-level edits via headless Claude Code (moplan-pattern)

Pivot the original "Marimo wraps run_apply" plan to a moplan-style **section-level review** layer that runs AFTER the 3-phase apply pipeline (gather → draft → render) has produced per-slug YAMLs under `//documents/`. Quarto is kept in the system but demoted to "PDF-only" (the very last step). The Marimo notebook + `mo.sidebar` + `mo.ui.chat` + headless Claude Code (subprocess of `claude -p`, with Anthropic SDK fallback) lets the user tweak individual resume sections — bullets in `work.yml`, the summary in `author.yml`, skills in `skill.yml` — without rerunning gather or draft. moplan (`/Users/shakes/DevProjects/moplan/plugin/notebooks/`) is the **explicit reference implementation**: `claude_chat.py`, `amendment_parser.py`, `moplan_store.py`, and `plan_ui.py:render_chat_history_bubbles()` are direct ports with thin domain-specific adapters. State model is hybrid: YAML on disk = source of truth (hand-editable, diffable, mergeable); SQLite = chat history + amendment statuses + Claude Code session UUIDs; in-memory dict = derived from YAML at startup, never mutated until Finalize (atomic write-tmp-then-rename).

Problem

jobsmith's apply pipeline lands per-slug YAMLs (`work.yml`, `education.yml`, `skill.yml`, `author.yml`) under `<applications_dir>/<slug>/documents/`, plus `index.qmd` and `documents/resume.qmd`. Today, fixing a single bullet means re-running `jobsmith apply` (3 phases × multiple specialists × minutes each) or hand-editing a YAML and re-rendering. There is no interactive review surface for "tweak this bullet, regenerate just the PDF." The earlier plan-807d44a7 v1 proposed a Marimo wrapper around `run_apply` with a live progress display, which solves the *observability* problem but not the *iterate-on-output* problem. Meanwhile, moplan (sister project at `/Users/shakes/DevProjects/moplan`) has shipped a working pattern for section-level review with a chat sidebar, headless Claude Code subprocess, and amendment accept/reject flow over a YAML+SQLite hybrid store. That pattern is portable to jobsmith with minor adapters — the YAMLs are already the right shape.

Goals

  1. **Quarto kept, demoted to PDF renderer** — the system continues to use Quarto + Typst as the deterministic PDF generator. Marimo never replaces Quarto. The user flow is `apply → review → render PDF`, where the middle step is a new Marimo surface and the third step is the existing render path.
  2. **Marimo + mo.sidebar + mo.ui.chat as the review surface** — single notebook (`src/jobsmith/marimo/review.py` or PEP 723 inline script) that loads one slug's YAMLs, renders section cards in the main area, and pins a chat sidebar (`mo.sidebar(_items, width="480px")`) for directives.
  3. **Headless Claude Code via moplan's ClaudeChatBackend** — port `claude_chat.py` directly. Subprocess: `claude -p <message> --output-format stream-json --verbose --append-system-prompt <ctx> [--resume <session-id>]`. Daemon thread reads stdout JSON lines into `queue.Queue`; main thread yields text from `type=assistant` events, breaks on `type=result`. Anthropic SDK fallback when `claude` binary absent and `ANTHROPIC_API_KEY` is set. System prompt (resume context) injected via `--append-system-prompt` inside `<context>` XML tags — never in the user message (prompt-injection defense).
  4. **Section-level edits without rerunning the pipeline** — user types `REVISE bullet work[0].highlights[2]: tighten and quantify`; Claude streams prose + a structured directive; parser extracts `{section, operation, field, content}` (port of `amendment_parser.py:26-40`); amendment lands in SQLite as `action=proposed`; per-amendment `mo.ui.dropdown` chooses Pending / Accept / Reject; Finalize iterates accepted amendments, mutates the in-memory dict, and atomically writes YAML.
  5. **Hybrid YAML + SQLite state model (moplan pattern)** — YAMLs on disk are the source of truth. SQLite (`plan_feedback`-equivalent table renamed to `review_feedback`) holds chat turns, Claude session UUID, amendment statuses, and approvals. In-memory Python dict is derived from YAML at startup and never mutated until Finalize.
  6. **Atomic YAML writes** — port `moplan_store.py:236-245` write-tmp-then-rename pattern. Non-edited fields preserved verbatim. (Moplan's own finalize is non-atomic; jobsmith fixes this on port.)
  7. **`jobsmith review <slug>` CLI command** — shells out to `uv run --script src/jobsmith/marimo/review.py --slug <slug>` (PEP 723) or `marimo run` (extra-installed), opens browser. Consistent with how `jobsmith site serve` shells out to `quarto preview` (`cli.py:734-745`).
  8. **Reusable moplan modules ported with attribution** — `claude_chat.py` (domain-agnostic), `amendment_parser.py` (regex-only), `moplan_store.py` (renamed `review_store.py`, walk-up discovery + atomic write), `plan_ui.py:render_chat_history_bubbles()` copied as-is.

Constraints

  • **Quarto stays in the dependency graph** — the apply pipeline still ends in `documents/resume.qmd` + `documents/cover-letter.qmd` and a Quarto/Typst render. Marimo must not write QMD; its writes are scoped to `documents/*.yml`.
  • **`--append-system-prompt` requires a recent claude CLI** — moplan recon flags this. Validate the installed CLI version at notebook startup; fall back to embedding context as the first user turn if the flag is unsupported (with a banner warning).
  • **`--resume <uuid>` brittleness** — Claude Code sessions expire; on `--resume` failure, retry without `--resume` (loses turn context, surfaced as a banner). Port moplan's retry logic.
  • **`marimo>=0.22.4` hard requirement** — `mo.sidebar` and `mo.ui.chat` (stock components) require this floor. Pin in the `[ui]` extra in `pyproject.toml`.
  • **No streaming cancellation upstream** — moplan uses a 60s `queue.Queue.get(timeout=60)` as the only circuit breaker. Decide v1 cancel UX in q-streaming-cancellation.
  • **Amendment ID dedup must be stable** — moplan uses Python `hash()`, which is randomized per interpreter restart (PYTHONHASHSEED). jobsmith MUST use UUID4 or a per-slug sequential counter persisted in SQLite.
  • **Atomic YAML write — non-negotiable** — write to `documents/<file>.yml.tmp`, fsync, then `os.replace` to the final path. Preserves non-edited fields. Moplan's own finalize is non-atomic; jobsmith fixes this on port.
  • **AnyWidget ESM from CDN breaks offline** — only relevant if jobsmith adds custom widgets. v1 uses stock marimo components only; defer custom widgets.
  • **Single-user, local-only** — `marimo run` on `localhost:2718`, no auth. Document the threat model: anyone with localhost access can read all per-slug YAMLs and invoke Claude Code with the project as cwd.
  • **`marimo` and `anywidget` add dependencies** — land as a `[project.optional-dependencies] ui` extra (extras already exist: `tui`, `test`, `dev`). Core install stays small; CLI-only path preserved.
  • **Existing per-slug YAML schema is the contract** — `work.yml`, `education.yml`, `skill.yml`, `author.yml` shapes are already produced by the apply pipeline. Marimo READS them as-is and writes back the same shape. No migration. Schema discovery lives in a shared loader module.
  • **Claude Code subprocess `cwd` must be the jobsmith project root**, not the slug directory — so the agent can read specialist contracts and the rest of the project context. moplan does the same.
  • **System-prompt context payload size** — too much context (entire YAML dump per turn) blows token budgets. Strategy: include only the section the user references plus a project-wide YAML index. Confirm strategy in q-context-payload.

#4 Finalize: atomic YAML write back to documents/*.yml M High Pending
What

Add a "Finalize accepted edits" mo.ui.run_button to the notebook. On click: (1) read all action="accepted" amendments from review_store for the current slug; (2) starting from the in-memory ResumeDocuments dict (loaded in slice 1), apply each amendment in order — mutating only the addressed section/field; (3) for each modified YAML file, serialize to documents/<file>.yml.tmp, fsync, then os.replace to the final path (atomic). Non-edited fields preserved verbatim — use ruamel.yaml (or already-vendored YAML lib) with round-trip mode to preserve key order, comments, and quoting. Port the atomic write helper from moplan_store.py:236-245 (FIX: moplan's own finalize is non-atomic; this is where jobsmith corrects the upstream bug). After Finalize, mark amendments action="finalized" in SQLite (preserves history; running Finalize again is a no-op for already-finalized rows). Surface a summary mo.callout listing which files were rewritten and which were untouched.

Why

Closes the write loop. Atomicity matters because the user may have a Quarto render in flight that reads documents/*.yml. Round-trip YAML preserves the apply pipeline's formatting choices (comments, key order) so diffs in git remain minimal and reviewable. moplan's non-atomic finalize is a known bug — jobsmith fixes it on port.

src/jobsmith/marimo/finalize.py, src/jobsmith/marimo/review.py, tests/test_marimo_finalize.py

  • Round-trip serialization preserves key order, top-of-file comments, and quoting style (`ruamel.yaml` round-trip mode or equivalent).
  • Atomic write: write-tmp + fsync + `os.replace`. A simulated crash between `os.replace` calls leaves the previous YAML intact (verified by killing the test mid-finalize).

Synthesis

v1 (run_apply wrapper) and v2 (post-pipeline review) solve different problems. v2 is the right pivot given (a) the per-slug YAMLs already exist and are the right shape; (b) moplan has done the hard architectural work and the port surface is well-defined; (c) the user pain point is "fix one bullet without rerunning gather/draft," which v1 didn't address. The plan preserves what's reusable from v1 (extras, CLI subcommand pattern, package location, config resolution) and replaces the apply-renderer+progress slices with the chat+parse+store+finalize stack. Two upstream moplan bugs (hash-based dedup, non-atomic finalize) are fixed on port. The eight open questions are real design choices the user should weigh in on before slice 1 starts; the most consequential are q-state-db-location (per-slug vs. user-wide), q-pep723 (PEP 723 vs. extras), and q-context-payload (token budget management).
