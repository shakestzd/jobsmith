Plan: Capture CLI apply runs in the web front-end live event stream (2 tiers)

DesignPending

Problem

CLI `jobsmith apply` (and onboarding) runs are invisible in the web UI's live event stream. The front end's stream is fed by the server's in-memory RunSupervisor, which only sees runs launched in-process via POST /api/applications. CLI runs execute out-of-process, render to the terminal (ApplyRenderer), and never register — so the UI shows nothing live, only post-hoc DB state on refresh. The CLI already writes coarse state (apply_runs.phase, specialist_outputs) to the shared DB, but the front end only subscribes per-slug (detail page), never at the list level.

Goals

  1. Tier 1: any active run (incl. CLI) appears live on the list view with phase-level progress, no manual refresh and no pipeline changes.
  2. Tier 2: CLI/onboarding runs stream the same fine-grained per-agent events as server runs, via a DB-backed event log (DB as single source of truth).
  3. Producer-agnostic capture: CLI apply, server in-process, and future remote runs all surface uniformly.
  4. Bounded storage: per-event log capped per run and pruned on terminal status.

Constraints

  • No new runtime dependency — stdlib + existing FastAPI/sse_starlette/SQLite stack.
  • WAL DB must keep handling concurrent CLI-writer + server-reader (already the case); sink writes are best-effort and never abort a run.
  • Backward compatible: existing per-slug /api/applications/{slug}/events behavior and tests unchanged; migrations idempotent on existing DBs.
  • Front end bundles via Vite to web_dist (hatch); localhost auto-auth shim feeds the SSE token.

#1 Global active-runs SSE feed — /api/runs/events (Tier 1) Add an all-slugs SSE endpoint GET /api/runs/events that streams M Med Complex Pending 1 Q
What

Add an all-slugs SSE endpoint GET /api/runs/events that streams active-run + phase + specialist events across every slug, reusing the existing DB poll (events_poll._db_poll_once) instead of per-slug subscription. Producer-agnostic: any writer of apply_runs / specialist_outputs (CLI apply, server in-process, onboarding) surfaces. Emits run/phase/status/specialist events with run_id + slug so the list view can route them. Keep the per-slug /api/applications/{slug}/events endpoint untouched.

Why

CLI jobsmith apply already writes apply_runs.phase + specialist_outputs live, but the front end only subscribes per-slug (detail page), so a CLI run is invisible on the list. A global feed makes any active run appear live with zero pipeline changes.

Files
src/jobsmith/api/events.py, src/jobsmith/api/events_poll.py, src/jobsmith/api/main.py
Done when
  • GET /api/runs/events opens an SSE stream and emits a phase event when any apply_runs row changes phase/status, regardless of slug
  • A specialist_outputs insert for any run surfaces as a specialist event carrying run_id + slug within one poll interval
  • The existing per-slug /api/applications/{slug}/events behavior and tests are unchanged
Decisions

Trigger: new all-slugs SSE route backed by the existing DB poll; no supervisor coupling so out-of-process producers (CLI) are captured. State: none new — reads apply_runs + specialist_outputs (already written live by both run paths). Payload: event {kind, run_id, slug, phase, status, [specialist,kind]}. Rejected: wildcard mode on the per-slug endpoint (overloads one route's semantics, harder to authorize/test); push from supervisor (misses out-of-process CLI runs entirely — the whole point).

#3 run_events table + append writer + retention (Tier 2 foundation) Add migration for an append-only runevents table M Med Complex Pending 1 Q
What

Add migration for an append-only run_events table (rowid PK, run_id, slug, seq, ts, kind, phase, payload_json) indexed for poll-by-rowid and by run_id. Add a small store helper to append an event and a retention routine that, on terminal run status, trims a run's events to a bounded tail (keep last N) — full fidelity while active, small table at rest.

Why

Per-agent live parity (Tier 2) needs a pollable per-event log; apply_runs only carries coarse phase. A purpose-built table keeps event semantics clean and bounded.

Files
src/jobsmith/migrations/010_run_events.sql, src/jobsmith/reuse/store.py, src/jobsmith/db.py
Done when
  • Migration 010 creates run_events with indexes on (rowid) and (run_id) and applies idempotently on a fresh and an existing DB
  • append_run_event() inserts a monotonic per-run seq row; reads by rowid return events in emission order
  • On terminal status, retention trims a run's events to the configured tail without touching active runs
Decisions

State: new append-only run_events table (canonical event log); rebuildable is N/A — it is the source for live streaming, not derived. Payload: {run_id, slug, seq, ts, kind, phase, payload_json}. Retention: cap per-run + prune on terminal status (keep last N). Rejected: reuse apply_state_log (modeled for state snapshots, not an event stream — semantic overload + poll ambiguity); unbounded keep (table growth); time-based prune (unbounded between sweeps).

#4 DB-writing EventSink fan-out on CLI + onboarding runs (Tier 2) Add a DbEventSink (implements the EventSink protocol) that appends each M Med Complex Pending 1 Q
What

Add a DbEventSink (implements the EventSink protocol) that appends each PipelineEvent to run_events via append_run_event. Compose it as a fan-out alongside the existing terminal ApplyRenderer using the CallbackEventSink/fan-out helper, so the CLI apply path (_cli_apply._run_apply_phases) and the onboarding run path emit to BOTH the terminal and the DB. Best-effort: a sink write error never aborts the pipeline.

Why

This is what makes out-of-process CLI (and onboarding) runs produce the same fine-grained PipelineEvents the in-memory supervisor gives server runs — captured uniformly in the DB.

Files
src/jobsmith/core/sinks.py, src/jobsmith/_cli_apply.py, src/jobsmith/core/pipeline.py
Done when
  • A CLI apply run writes one run_events row per PipelineEvent it emits, in order, tagged with run_id + slug
  • The terminal ApplyRenderer output is unchanged (fan-out, not replacement)
  • A DbEventSink write failure is swallowed and the run continues (no BackstopError/abort from sink errors)
Decisions

Trigger: fan-out EventSink wired wherever events= is currently the ApplyRenderer (CLI apply + onboarding). State: writes run_events (slice-3); no other state. Payload: serialized PipelineEvent (kind, phase, name, payload). Rejected: replace ApplyRenderer with DbEventSink (loses terminal UX); IPC from CLI to the server supervisor (requires server running + couples processes — DB fan-out is decoupled and always works).
