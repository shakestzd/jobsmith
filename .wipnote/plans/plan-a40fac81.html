Plan: Code-orchestrated local apply: Python DAG + per-node LLM backends

Pivot from plan-21911e16. The slice-1 spike proved a 4B local gemma CANNOT drive Claude Code's 70-tool agentic apply loop (it looped on step 1; ~5 tok/s; 0 artifacts in 26 min) — NO-GO for "model drives Claude Code". The POC proved the inverted design: Python owns the apply DAG and the model does ONE bounded JSON task per node (a real jd-parse node produced a valid jd-parsed.json in 49.6s, first try). This plan builds a no-framework, code-owned state-machine driver for the LOCAL apply path with per-node backends (local gemma via the existing OpenAICompat client + cloud Claude via the anthropic SDK). v1 = the gather->draft core (5 nodes). The existing claude -p cloud apply is untouched. Supersedes plan-21911e16 slices 2-6.

DesignPending

Problem

jobsmith's apply pipeline is implemented as Claude Code specialist sub-agents driven by `claude -p` (headless.py + the apply-*.md agents). plan-21911e16 tried to keep that harness and point it at a local gemma via vllm-mlx; the spike (docs/spikes/ byo-model-apply.md) proved a 4B model has tool *fidelity* (single tool_use blocks are well-formed) but not agentic *planning* — it loops on the orchestrator's first step and never advances, and at ~5 tok/s a many-turn loop is impractical regardless. So the local path needs a different harness: code owns orchestration; the model does narrow, single-shot, schema-constrained tasks.

Goals

  1. Build a no-framework, Python-owned state-machine driver that executes the existing apply DAG (specialist-contracts.yaml pipeline.stages) for the LOCAL path, with each specialist reduced to a code Node that makes ONE bounded structured-JSON call.
  2. Provide a per-node Backend abstraction with two impls — OpenAICompatBackend (local gemma via vllm-mlx, reusing src/jobsmith/llm/openai_compat.py) and AnthropicBackend (cloud Claude via the anthropic SDK, tool_use structured output) — so any node can run local or cloud.
  3. Ship v1 as the gather->draft core (jd-parse, fit-score, bullet-select, prose-write, prose-qa) end-to-end on local gemma, with .apply-state/ JSON checkpoints for crash-resume and a config-gated on_failure policy.
  4. Leave the existing claude -p cloud apply path completely unchanged (no regression); the code-driver is a separate, config-selected orchestration for the local/hybrid path.

Constraints

  • Reuse the existing JSON-from-weak-model machinery (openai_compat.py + the llm_rescore.py robust-parse pattern — json_schema response_format AND schema-in-prompt AND robust parse; flag parse_ok=False, never raise). vllm-mlx enforces response_format server-side, but a 4B honors it only as well as the server does, so robust-parse stays the safety net.
  • vllm-mlx engine — do NOT pass --continuous-batching for gemma-4 (it crashes the MLLM attention path with a shared_kv TypeError -> 0 tokens); REQUIRE --enable-auto-tool-choice --tool-call-parser gemma4 --reasoning-parser gemma4. (Proven in the spike.)
  • Lean dependencies — httpx is already in-tree; the only new runtime dep is the `anthropic` SDK (MIT, ~8 transitive). Optional `tenacity` (0 deps) for retry. Do NOT add LiteLLM — 1.82.7/1.82.8 shipped a confirmed credential-stealer (GHSA-5mg7-485q-xm76) — and do NOT add a heavy agent framework (LangGraph/CrewAI) for a fixed 13-node DAG.
  • Default apply behavior is unchanged — the orchestrator selector defaults to the existing cloud claude -p path; the code-driver is opt-in.

What

New package src/jobsmith/apply_local/. driver.py defines: Node (one bounded LLM task — name, output pydantic model, json_schema, bounded reask loop, returns validated obj + parse_ok), and Pipeline (executes an ordered stage list with sequential + fan-out (ThreadPoolExecutor) stages and bounded counter loops). checkpoint.py persists each node result to applications/{slug}/.apply-state/<name>.json (the EXISTING per-application state dir from specialist-contracts.yaml, slug threaded in) and skips a node whose checkpoint exists (crash-resume). Productionizes scripts/_apply_local_poc.py. No specialist logic here — pure orchestration primitives.

Why

This is the spine of the inverted harness: Python owns control flow (sequencing, fan-out, bounded loops, resume) so the model never has to plan. Proven viable by the POC; this slice makes it a tested module.

Files
src/jobsmith/apply_local/__init__.py, src/jobsmith/apply_local/driver.py, src/jobsmith/apply_local/checkpoint.py, tests/test_apply_local_driver.py
Done when
  • Pipeline runs an ordered list of stages — a sequential stage runs its node; a fan-out stage runs N nodes concurrently and joins; a loop stage re-runs its node until an ok-predicate or a max-iteration cap.
  • A node whose applications/{slug}/.apply-state/<name>.json checkpoint already exists AND was written with parse_ok=true is skipped and its cached result returned (resume); a parse_ok=false result is NOT treated as a final checkpoint (re-run on resume); a fresh run writes the checkpoint atomically.
  • Node.run does a bounded reask (default 3) on invalid or unparseable JSON and returns (obj, parse_ok) — never raises on a single bad generation.
Decisions

Trigger: an apply run in code_local orchestration mode constructs a Pipeline of nodes. State: applications/{slug}/.apply-state/<name>.json per node (the existing specialist-contracts state convention) = the resume ledger; no global mutable state. Payload: validated per-node objects threaded to downstream nodes. Rejected: LangGraph/Burr/Haystack (framework weight + lock-in for a fixed DAG); a generic workflow engine (Prefect/Dagster — wrong altitude); letting the model decide the next step (the spike NO-GO).

#2 Per-node LLM Backend abstraction: OpenAICompatBackend + AnthropicBackend src/jobsmith/applylocal/backends.py defines a Backend protocol: M Med Complex Pending 2 issues 1 Q
What

src/jobsmith/apply_local/backends.py defines a Backend protocol: complete_structured(messages, schema, *, temperature) -> (raw, parse_ok). Two impls: OpenAICompatBackend wraps the existing jobsmith.llm.openai_compat.OpenAICompatClient (local gemma via vllm-mlx, or any OpenAI-compatible incl. Claude's OpenAI-compat endpoint); AnthropicBackend uses the anthropic SDK Messages API with a single tool (input_schema = the node schema) to force structured output, mapping tool_use back to a dict. Both share the llm_rescore robust-parse helpers (strip fence -> loads -> substring fallback). A factory resolves a Backend from config (provider + base_url/model/api_key).

Why

Goal 2 — the same node body runs on local gemma or cloud Claude by swapping the Backend. Native anthropic backend (user choice) makes cloud Claude a first-class per-node drop-in.

Files
src/jobsmith/apply_local/backends.py, tests/test_apply_local_backends.py, pyproject.toml
Done when
  • OpenAICompatBackend.complete_structured posts json_schema response_format to the configured base_url and returns (parsed_dict, parse_ok) using the shared robust-parse; parse_ok=False (not an exception) on unparseable content.
  • AnthropicBackend.complete_structured calls the anthropic SDK with one tool whose input_schema is the node schema, forces tool_use, and returns the tool input as the parsed dict; a text-only (no tool_use) reply yields parse_ok=False.
  • A backend factory selects the impl from config (claude_cloud->Anthropic, openai_compatible/local->OpenAICompat) without the caller importing either class.
Decisions

Trigger: each Node.run calls Backend.complete_structured for its one task. State: stateless clients; config carries base_url/model/api_key per provider. Payload: (parsed_dict, parse_ok) — uniform across backends so nodes are backend-agnostic. Rejected: OpenAI-compat-only for cloud (loses native Claude tool_use fidelity — user chose native anthropic); LiteLLM as a universal gateway (malware advisory GHSA-5mg7-485q-xm76); raising on bad JSON (the pipeline must degrade, not crash).
