## Bugs Found

### BUG-1: All specialists shown as "queued" on Specialists tab

**Title:** Specialists tab renders every specialist with "queued" status regardless of actual state  
**Severity:** MAJOR  
**Component:** Frontend — Specialists tab / run detail view  

**Repro steps:**
1. Navigate to http://localhost:5173
2. Open any application that has a completed or failed run (e.g., `reddit-senior-analytics-engineer`)
3. Click the Specialists tab

**Expected:** Each specialist card shows its actual completion state. For `reddit-senior-analytics-engineer` (run `97103e0f-f7d7-410a-8ac4-71936460dd6b`), all 8 specialists (`apply-jd-parser`, `apply-fit-scorer`, `apply-hm-enricher`, `apply-bullet-selector`, `apply-company-research`, `apply-prose-writer`, `apply-prose-qa`, `prose-draft.agent.md`) have non-null `output` in the artifacts endpoint and should show as completed/succeeded.

**Actual:** All specialists display as "queued".

**Likely cause:** The frontend derives specialist display status from a field that is not populated or from an endpoint that does not return status data. The `/api/applications/{slug}/runs/{run_id}/snapshot` endpoint returns `{"detail": "Method Not Allowed"}` for all tested slugs (see BUG-2), which may be the intended status source. Alternatively, the frontend maps specialist status from `apply_runs.phase` which is `unknown` for all runs in the DB.

### BUG-2: Snapshot endpoint returns 405 Method Not Allowed

**Title:** `GET /api/applications/{slug}/runs/{run_id}/snapshot` returns 405 for all applications  
**Severity:** MAJOR  
**Component:** API — snapshot route  

**Repro steps:**
1. `GET /api/applications/reddit-senior-analytics-engineer/runs/97103e0f-f7d7-410a-8ac4-71936460dd6b/snapshot` with valid auth header

**Expected:** 200 with run snapshot JSON including specialist statuses.

**Actual:** `{"detail": "Method Not Allowed"}` (HTTP 405).

**Note:** The route is registered in the OpenAPI schema (`/api/applications/{slug}/runs/{run_id}/snapshot`), meaning the path resolves but the HTTP method is rejected — likely `POST` only, not `GET`, or the route has an incorrect method decorator.

---

### BUG-3: `apply_runs.phase` stuck at "unknown" for all runs

**Title:** All apply runs have `phase = "unknown"` in the database  
**Severity:** MAJOR  
**Component:** Backend — phase tracking  

**Evidence:** `SELECT phase, status FROM apply_runs ORDER BY started_at DESC LIMIT 5` returns `unknown|failed` for every row. This means the phase transition events are either not being written to `apply_runs` or the column update is not being committed.

**Expected:** Runs that progressed through phases should have a terminal phase value (e.g., `prose`, `qa`, `complete`) reflecting the last phase reached before failure.

**Actual:** Phase is `unknown` for all 28 runs in the DB.

**Impact:** The frontend Specialists tab bug (BUG-1) may be a downstream consequence — if the frontend reads phase from `apply_runs.phase` to infer specialist progress, it will always show pre-start state.

## Recommendations

1. **Fix snapshot endpoint (BUG-2 first):** Confirm whether `/api/applications/{slug}/runs/{run_id}/snapshot` expects `POST` or `GET`. If it is `GET`, check the route decorator. This is likely a one-line fix and may unblock the Specialists tab rendering.

2. **Fix phase persistence (BUG-3):** The phase update to `apply_runs` is not being committed. Audit the phase transition code path (`src/jobsmith/`) for missing `conn.commit()` calls or exception-swallowing around the `UPDATE apply_runs SET phase = ?` statement.

3. **Re-test Specialists tab after BUG-2/3 fixes (BUG-1):** Once the snapshot endpoint works and phase is populated, re-check whether specialist statuses render correctly. The "queued" symptom is most likely a consequence of missing data rather than a UI logic error.

4. **Audit `.apply-state/` creation timestamps (BUG-4):** Run `find /Users/shakes/DevProjects/JobApplications/private -name ".apply-state" -newer <migration-date-sentinel-file>` to confirm no new directories were created post-0.8.5. If any are newer, trace which code path is still writing to `.apply-state/` instead of the DB.

5. **Manual browser console pass:** Open `http://localhost:5173`, navigate to a run detail page, open DevTools Network + Console, and document any 4xx/5xx responses and JS errors. This will confirm whether the Specialists tab failure produces a logged error.

6. **All four API-listed applications are in `failed` status:** Investigate whether this reflects genuine run failures (agent errors) or a status field migration gap. If the apply pipeline completed 8 specialists successfully for `reddit-senior-analytics-engineer` but the run is `failed`, the failure is likely in a late phase (prose-qa or final assembly).
